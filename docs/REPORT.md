# 项目完成报告

## 1. 项目目标

完成课程大作业第一阶段：用 MongoDB 实现一个简化版在线问卷系统。
核心目标不是只做页面，而是把「问卷结构、跳转规则、填写状态、统计口径」
都落在数据库模型和服务端逻辑中，并保证：

- 用户可以注册登录，只能管理自己的问卷；
- 问卷可以发布、关闭、设置截止时间，并通过公开链接分享；
- 支持单选、多选、文本、数字四种题型及各自校验；
- 单选、多选、数字的跳转可配置，不在代码中写死；
- 填写过程逐题保存，支持匿名和重复提交控制；
- 创建者可以查看整卷与单题统计；
- 代码、数据库设计、测试、文档、AI 日志完整可交付。

## 2. 技术选型

| 层次 | 选择 | 理由 |
| --- | --- | --- |
| 后端 | Python 3 + Flask 3 | 轻量、路由清晰，适合课程项目 |
| 数据库 | MongoDB 8 + PyMongo | 文档模型适合问卷这种嵌套结构 |
| 页面 | Jinja2 服务端渲染 | 不引入前端构建链，便于阅读和答辩 |
| 认证 | Werkzeug 密码哈希 + 签名会话 | Flask 自带能力，够用且安全 |
| 测试 | pytest + requests | 单元/集成 + 真实 HTTP 两层验证 |

## 3. 系统设计

### 3.1 模块划分

```text
app.py            应用工厂、CSRF、模板过滤器、错误页
config.py         配置与环境变量
db.py             连接、集合常量、索引
auth.py           注册/登录/退出、登录态
surveys.py        问卷、题目、跳转规则管理
fill.py           开始、逐题作答、检查、提交、放弃
logic.py          答案规范化、规则匹配、下一题计算
stats_service.py  聚合统计
stats.py          统计页面与分页
utils.py          时间、ID、解析、展示、HMAC
```

### 3.2 请求流程

```text
登录用户 → 创建问卷（draft）→ 添加题目 → 配置跳转规则 → 发布
       → 分享 /survey/<public_id>
回答者 → 登录 → 开始填写（创建 response 草稿）
       → 逐题作答（保存 answers/path/current_question_id）
       → 检查 → 提交（status=submitted）
创建者 → /surveys/<id>/stats → 聚合 responses 查看统计
```

## 4. MongoDB 设计

### 4.1 四个集合

| 集合 | 主要内容 | 关系 |
| --- | --- | --- |
| `users` | 账号、密码哈希 | 被 surveys.owner_id、responses.respondent_id 引用 |
| `surveys` | 标题、说明、匿名/重复开关、状态、截止时间、公开链接 | 引用 owner_id |
| `questions` | 题型、标题、选项、配置、跳转规则 | 引用 survey_id |
| `responses` | 答案、实际路径、状态、匿名标识、时间 | 引用 survey_id、respondent_id |

### 4.2 内嵌与引用

**内嵌**：

- 选项内嵌在题目：选项总是和题目一起读写，数量有限；
- 跳转规则内嵌在题目：规则只属于该题，按顺序匹配方便；
- 答案内嵌在答卷：一次填写的答案总是一起读取、提交、统计；
- `path` 内嵌在答卷：记录实际经过的题目，和答案同生命周期。

**引用**：

- `owner_id` 引用用户：用户信息独立，问卷按 owner 查询；
- `respondent_id` 引用用户：实名答卷需要关联；匿名时删除；
- `survey_id` 引用问卷：题目和答卷会增长，按问卷查询和统计。

这样既不是“所有数据一个集合”，也不是“每个选项/答案一个集合”。
前者会导致文档过大、更新竞争和权限难控；后者会导致大量关联查询。

### 4.3 索引

| 索引 | 用途 |
| --- | --- |
| `users.username` 唯一 | 注册去重、登录查找 |
| `surveys.public_id` 唯一 | 公开链接定位 |
| `surveys(owner_id, created_at desc)` | 创建者问卷列表 |
| `questions(survey_id, order)` 唯一 | 按顺序读题、防止顺序冲突 |
| `responses(survey_id, status)` | 统计已提交答卷 |
| `responses(survey_id, respondent_id, status)` | 找草稿/提交 |
| `responses(survey_id, respondent_key, status)` | 匿名去重 |
| `responses.answers.question_id` 多键 | 按题目统计 |
| `(survey_id, respondent_id)` 部分唯一，条件 `in_progress` | 最多一份草稿 |

统计不保存冗余计数字段，而是查询时聚合，避免并发更新不一致。

## 5. 跳转设计

### 5.1 规则结构

```json
{
  "condition": {"operator": "gte", "value": 18},
  "target": "end"
}
```

支持的运算符：

- 单选：`equals`、`not_equals`；
- 多选：`contains`、`not_contains`、`count_gte`、`count_lte`、`count_eq`；
- 数字：`lt`、`lte`、`eq`、`gte`、`gt`。

### 5.2 执行

```text
按 jump_rules 顺序检查
  ├── 命中且 target=end → 结束
  ├── 命中且 target=后续题目 → 跳到该题
  └── 都不命中 → 按 order 进入下一题
```

设计要点：

- 规则从数据库读取，代码中没有针对某道题的 `if`；
- 只允许跳到后面的题目或 `end`，避免循环；
- 目标在保存时校验，发布前全量校验；
- 每次作答把当前题追加到 `path`，提交时按 `path` 校验答案，
  因此被跳过的必答题不会被误判为缺失。

## 6. 校验设计

三层校验：

1. **HTML 约束**：`required`、`minlength`、`maxlength`、`min`、`max`；
2. **服务端答案校验**：`logic.normalize_answer`；
3. **业务状态校验**：发布/关闭/截止、重复提交、权限归属。

具体规则：

| 场景 | 规则 |
| --- | --- |
| 单选 | 必答非空；值必须是已有选项 key |
| 多选 | 去重、按选项顺序保存；满足 min/max；不能含非法 key |
| 文本 | 必答不能全空白；检查 min/max 长度 |
| 数字 | 可解析；整数模式拒绝小数/指数；检查范围；拒绝 NaN/Infinity |
| 题目配置 | 选择题至少 2 项；多选 min/max 不矛盾且不超过选项总数；文本/数字 min/max 不矛盾 |
| 跳转规则 | 运算符匹配题型；选项存在；数量/数值合法；目标在后 |
| 发布 | 至少一题；所有规则通过 |
| 填写 | 已发布、未关闭、未截止；重复提交控制 |
| 权限 | 只能操作自己的问卷；越权 404 |

本次重新实现特别补上了「多选最少选择数量不能超过选项总数」的边界校验，
避免创建永远无法作答的题目。

## 7. 填写、并发与匿名

- 开始填写创建 `in_progress` 草稿；
- 每次作答立即更新答案、路径、当前题；
- 提交用条件更新 `{"_id": draft, "status": "in_progress"}`，只有一个请求能成功；
- 部分唯一索引防止并发创建多份草稿；
- 匿名提交删除 `respondent_id`，写入 HMAC `respondent_key`；
- 重复提交检查同时查实名 ID 和匿名 key；
- 旧页面提交错误 `question_id` 会被忽略。

## 8. 统计设计

- 只统计 `status=submitted`；
- 单选：按选项分组计数；
- 多选：先展开答案数组，再按选项分组；
- 文本：按提交时间倒序分页；
- 数字：`avg/min/max/count` + 明细分页；
- 百分比分母是实际回答该题的人数；
- 草稿不计入；
- 空数据页面正常显示提示。

## 10. 遇到的问题与解决

| 问题 | 现象 | 解决 |
| --- | --- | --- |
| MongoDB 未启动 | PyMongo 连接被拒绝 | 启动 `mongod`，README 写明启动命令 |
| 选项 key 按位置复用 | 调整选项顺序后规则指向错误选项 | 按选项文本保留旧 key，重排不会错位 |
| 发布后仍可改结构 | 已有答卷会因题目变化失真 | 发布后锁定题目和规则，只允许改截止时间/关闭 |
| 匿名与限填一次冲突 | 删除用户 ID 后无法判断是否提交过 | 使用 HMAC `respondent_key` 去重 |
| 并发开始填写 | 可能创建多份草稿 | 部分唯一索引 + `DuplicateKeyError` 恢复 |
| 文本答案只能看前 N 条 | 不满足“查看所有填写内容” | 增加分页，页码越界回退 |
| 多选最少数量可超过选项数 | 创建出无法作答的题目 | 增加配置校验和测试 |
| CSRF 未覆盖 | 测试默认关闭 CSRF | 单独用例开启 CSRF 验证 |

## 11. AI 使用过程

本次重新实现按 [PROMPTS.md](PROMPTS.md) 的 16 步进行：
读需求 → 定范围 → 设计集合 → 设计索引 → 设计跳转 → 列校验 → 搭骨架 →
认证 → 问卷/题目 → 填写 → 统计 → 测试 → E2E → 文档 → 自审 → 答辩准备。

AI 负责：

- 根据需求生成代码、页面、测试和文档初稿；
- 运行测试、定位失败并修复；
- 生成真实 HTTP 冒烟脚本；
- 记录命令和实际输出。

用户负责：

- 选择「重新实现」方案，明确不删除原项目历史；
- 要求日志必须真实，不把重新实现伪装成第一次实验；
- 确定只做第一阶段；
- 验收测试结果和提交材料。

详细记录见 [AI_LOG.md](AI_LOG.md)。

## 12. 已知限制与扩展

- 文本题不支持跳转（课程只要求单选、多选、数字）；
- 跳转只能向后，不支持回跳/循环；
- 发布后题目结构锁定；
- 未实现答案导出、图表、邮件通知；
- 生产部署需要 WSGI 服务器、强随机 `SECRET_KEY`、MongoDB 副本集和备份。

第二阶段可扩展：题目版本化、回跳/循环、答案导出、图表报表、多语言、邮件通知。
